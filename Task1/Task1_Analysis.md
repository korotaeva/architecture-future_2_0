# Задание 1: Анализ и приоритизация проблем

## Диаграмма контейнеров (C4 Model, Уровень 2)

*(Диаграмма отрисована в PlantUML, Draw.io или аналогичном инструменте и сохранена как `Future_2_0_Container_Diagram.png`)*

**Описание диаграммы:**
Система разделена на несколько bounded context'ов (доменов) с четкими границами. Центральным элементом является **Портал самообслуживания (Data Marketplace)**, который предоставляет единую точку доступа к данным для аналитиков и бизнес-пользователей. Данные поступают из независимых доменов через их выделенные **Data Product API**.
1.  **Домен "Клиники & Медицина"**: Предоставляет обезличенные медицинские данные, справочники (врачи, клиники, инвентарь) через свой API. Хранит детальные медицинские карты локально, не выгружая их в общее пространство.
2.  **Домен "Финтех"**: Предоставляет финансовые данные (счета, транзакции, кредиты) через свой API. Полностью независимый сервис, отвечающий за свою предметную область.
3.  **Домен "ИИ-Сервисы"**: Потребляет данные из доменов "Клиники" и "Финтех" через их API для обучения моделей и предоставляет результаты своей работы (например, прогнозы) как Data Product.
4.  **Управляемый Data Lake / DWH**: Не является центральным хабом, а выполняет роль платформы для сложных кросс-доменных ETL-процессов и хранения исторических данных в сыром и очищенном виде. Потребляет данные из Data Product API каждого домена.
5.  **Портал самообслуживания (Data Marketplace)**: Предоставляет интерфейс для построения отчетов, используя унифицированные данные из Data Lake и прямые запросы к Data Product API. Интегрирован с Power BI.
6.  **Устаревший DWH (Legacy)**: Постепенно выводится из эксплуатации. На диаграмме показан как отдельный контейнер, от которого идут стрелки миграции данных в новый Data Lake и домены.

## Проблемные места текущей архитектуры (AS-IS)

| Проблема | Описание для бизнеса | Техническая причина |
| :--- | :--- | :--- |
| **Низкая скорость отчетности** | Сложные отчеты готовятся часами. Это замедляет принятие решений и снижает оперативность реакции на изменения рынка. | Монолитный DWH становится узким горлышком. Большое количество сложных трансформаций и джойнов на лету в единой базе данных. |
| **Высокая стоимость изменений** | Запуск нового продукта или интеграция нового партнера занимает месяцы и требует больших затрат. | Вся бизнес-логика зашита в DWH. Любое изменение требует глубоких знаний сложной системы и рискует сломать существующие процессы. |
| **Риски безопасности и compliance** | Сложно управлять доступом к данным. Медицинские и финансовые данные хранятся в одной системе, что может не соответствовать отраслевым стандартам (GDPR, HIPAA, 115-ФЗ). | Отсутствует изоляция доменов. Нет четкого разделения ответственности за данные между командами. |
| **Низкая надежность** | Проблема в DWH может "положить" все бизнес-направления одновременно: и клиники, и банк, и аналитику. | Единая точка отказа. Монолитная архитектура. |
| **Сложность развития** | Невозможно независимо развивать направления. Технологический стек устарел и не позволяет использовать современные практики. | Устаревшие технологии (SQL Server 2008, Power Builder), сильная связность компонентов. |

## Приоритизация проблем (Матрица Эйзенхауэра)

*   **Важно и Срочно (Сделать первым)**:
    *   **Низкая скорость отчетности.** Прямо сейчас бизнес теряет деньги и возможности из-за медленной аналитики. Это ключевая боль, ради решения которой инициирован проект.
    *   **Риски безопасности и compliance.** Юридические и репутационные риски могут привести к огромным штрафам и потере лицензий. Нельзя откладывать.

*   **Важно, но Не срочно (Запланировать)**:
    *   **Высокая стоимость изменений.** Это стратегическая проблема, которая мешает масштабированию бизнеса. Её решение — основная цель трансформации.
    *   **Низкая надежность.** Проблему нужно решать, но пока система работает, у нас есть время на плановый перенос нагрузки.

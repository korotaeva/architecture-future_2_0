# Задание 2: Обоснование разделения на домены

## Data Flow Diagram (DFD)

*(Диаграмма отрисована в Draw.io или аналогичном инструменте и сохранена как `Future_2_0_DFD.png`)*

**Описание DFD:**
Диаграмма показывает потоки данных между новыми доменами.
1.  **Домен "Клиники & Медицина"**: Внутри домена данные из медицинских систем (PACS, EMR) обрабатываются и обезличиваются. На выходе домен публикует два потока:
    *   **Обезличенные медицинские события** (например, факт оказания услуги, диагноз без привязки к личности) в **Управляемый Data Lake**.
    *   **Справочные данные** (врачи, клиники, оборудование) в **Портал самообслуживания** через API.
2.  **Домен "Финтех"**: Внутри обрабатывает все финансовые транзакции. Публикует:
    *   **Финансовые данные** (транзакции, балансы счетов) в **Управляемый Data Lake**.
    *   **Агрегированные финансовые показатели** (например, ежемесячный оборот по клинике) в **Портал самообслуживания** через API для оперативных отчетов.
3.  **Домен "ИИ-Сервисы"**:
    *   **Потребляет** данные из Data Lake и API других доменов.
    *   **Публикует** результаты своей работы (прогнозы, кластеризации) обратно в Data Lake и на Портал самообслуживания как новый data product.
4.  **Управляемый Data Lake**: Принимает сырые и очищенные данные из всех доменов. Здесь же происходят сложные кросс-доменные преобразования (ETL), результаты которых также становятся доступны на **Портале самообслуживания**.
5.  **Портал самообслуживания**: Агрегирует данные из всех источников (API доменов, Data Lake) и предоставляет единый интерфейс для построения отчетов.

## Логика разделения на домены и преимущества

**Принципы разделения:**
Разделение проведено по принципу ** bounded context** (ограниченного контекста) из методологии Domain-Driven Design (DDD). Каждый домен соответствует отдельной бизнес-способности компании:
1.  **"Клиники & Медицина"**: Способность оказывать медицинские услуги.
2.  **"Финтех"**: Способность оказывать финансовые услуги.
3.  **"ИИ-Сервисы"**: Способность создавать и предоставлять интеллектуальные сервисы на основе данных.

**Аргументация и преимущества:**

1.  **Независимость и скорость разработки (Time-to-Market)**
    *   *Как решает проблему:* Команды каждого домена могут независимо друг от друга разрабатывать, развертывать и масштабировать свои сервисы. Им больше не нужно координировать каждое изменение с командой центрального DWH.
    *   *Преимущество для бизнеса:* Новая фишка в банковском приложении или интеграция с новой фармацевтической компанией запускается в разы быстрее.

2.  **Масштабируемость и надежность**
    *   *Как решает проблему:* Нагрузка распределена между независимыми системами. Проблема в финтех-домене не затронет работу клиник. Каждый домен можно масштабировать аппаратно и программно в соответствии с его уникальными потребностями.
    *   *Преимущество для бизнеса:* Система становится устойчивее к сбоям и легко растущей нагрузке в каждом из направлений.

3.  **Data Ownership и безопасность**
    *   *Как решает проблему:* Каждая команда владеет своими данными и отвечает за их качество, безопасность и соответствие регуляторным требованиям (например, команда "Финтеха" за PCI DSS, команда "Клиник" за HIPAA). Доступ к данным предоставляется через строго описанные API.
    *   *Преимущество для бизнеса:* Резко снижаются合规ционные (compliance) риски. Легче проходить аудиты.

4.  **Устранение единой точки отказа (DWH)**
    *   *Как решает проблему:* DWH перестает быть центральным хабом. Его роль меняется на платформу для глубокой аналитики, а не для операционной работы.
    *   *Преимущество для бизнеса:* Операционная деятельность защищена от проблем в аналитической системе, и наоборот.

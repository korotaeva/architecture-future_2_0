# Задание 3: Технический радар, роадмап и обоснование изменений

## Технический радар

Технический радар визуализирует наш подход к технологиям: что мы принимаем, что оцениваем и от чего отказываемся.


### Категории и технологии

| Категория | Технология | Кольцо | Обоснование |
| :--- | :--- | :--- | :--- |
| **Архитектура** | Data Mesh | **Adopt** | Фундаментальный подход для масштабирования и устранения монолитного DWH как единой точки отказа и узкого горлышка. |
| **Архитектура** | Event-Driven | **Adopt** | Позволяет реагировать на события в реальном времени (например, новая транзакция, поставленный диагноз) и строить более оперативную аналитику. |
| **Архитектура** | API-First | **Adopt** | Обеспечивает стандартизованный, надежный и безопасный обмен данными между независимыми доменами. |
| **Хранилище** | MinIO + Apache Iceberg | **Adopt** | Формирует ядро современного Data Lakehouse. MinIO предоставляет дешевое и масштабируемое S3-совместимое хранилище. Iceberg добавляет управление метаданными, транзакционность и оптимизацию запросов поверх сырых данных. |
| **Обработка** | Apache Spark | **Adopt** | Де-факто стандарт для обработки больших данных. Критически важен для переноса и трансформации ETL-логики из старого DWH. |
| **Оркестрация** | Apache Airflow | **Adopt** | Позволяет описывать, планировать и мониторить сложные пайплайны данных в виде кода (Python), что обеспечивает повторяемость и надежность. |
| **Каталог данных** | DataHub | **Adopt** | Необходим для реализации Data Mesh. Позволяет обнаруживать данные, понимать их происхождение (lineage) и видеть, кто ими владеет. Основа для самообслуживания. |
| **Портал/SQL-Engine** | Dremio | **Trial** | Ключевой кандидат на роль портала самообслуживания. Позволяет бизнес-пользователям выполнять быстрые SQL-запросы к данным в Lakehouse без глубоких технических знаний. |
| **Верификация данных** | Great Expectations | **Trial** | Помогает автоматизировать проверку качества данных на стыке доменов через Data Contracts, обеспечивая доверие к данным в витринах. |
| **Шина данных** | Apache Camel (Legacy) | **Hold** | Устаревшее решение, которое будет замещено комбинацией асинхронной шины (Kafka) и синхронных API (gRPC, REST). |
| **Язык** | Power Builder | **Hold** | Устаревшая технология для UI. Его логика будет переписана на современные веб-технологии в новом портале самообслуживания. |

## Роадмап трансформации

Роадмап разбивает нашу стратегию на конкретные, измеримые этапы с указанием сроков и ответственных.


### Этапы и ключевые вехи

**Этап 1: Фундамент и пилот (Q1 2026)**
*   **Цель:** Создать базовую инфраструктуру и доказать жизнеспособность подхода на наименее рискованном домене.
*   **Результаты:**
    *   Развернуты Kubernetes, MinIO, Airflow.
    *   Запущен пилот с доменом "Финтех": его данные выгружены в Iceberg-таблицы.
    *   Построены первые прототипы витрин данных поверх Lakehouse.
*   **Ответственные:** Центральная платформенная команда, команда "Финтеха".

**Этап 2: Масштабирование и миграция (Q2-Q3 2026)**
*   **Цель:** Подключить ключевые домены и запустить портал самообслуживания.
*   **Результаты:**
    *   Домены "Клиники" и "Фармацевтика" подключены по модели Data Product.
    *   Запущена бета-версия портала самообслуживания на базе Dremio.
    *   Настроены основные API-шлюзы для межсервисного взаимодействия.
    *   Реализована базовая реаль-тайм обработка через Kafka.
*   **Ответственные:** Команды доменов, BI-разработчики.

**Этап 3: Внедрение управления Data Mesh (Q4 2026)**
*   **Цель:** Децентрализовать управление данными и обеспечить высочайшее качество.
*   **Результаты:**
    *   Назначены Data Product Owners в каждом домене.
    *   Внедрен DataHub как единый каталог данных.
    *   Внедрены Data Contracts и автоматизированные проверки качества (Great Expectations).
    *   Построены процессы федеративного управления.
*   **Ответственные:** Data Product Owners, платформенная команда.

**Этап 4: Оптимизация и подготовка к будущему (2027)**
*   **Цель:** Повышение эффективности и закладка основы для новых бизнес-возможностей.
*   **Результаты:**
    *   Постоянный мониторинг и оптимизация производительности дорогостоящих запросов.
    *   Развернута ML-платформа для расширенной аналитики.
    *   Архитектура готова к быстрой интеграции новых компаний через M&A.
*   **Ответственные:** Все команды.

## Обоснование изменений и логики последовательности

Предложенный план изменений не является произвольным набором технологий. Это строгая последовательность, направленная на минимизацию рисков и максимальное увеличение ценности для бизнеса на каждом шаге.

1.  **Этап 1: Сначала фундамент, потом все остальное.**
    *   *Зачем?* Бессмысленно предлагать доменам самостоятельно публиковать данные, если у них нет для этого простой и стандартной платформы. Сначала мы создаем "асфальтированную дорогу" (MinIO, Iceberg, Airflow), по которой потом смогут ездить все "машины" (домены). Пилот на домене "Финтех" выбран, потому что его команды уже работают с современными технологиями (Golang/Java), что снижает риски и ускоряет получение первого положительного результата.

2.  **Этап 2: Демонстрация ценности и вовлечение.**
    *   *Зачем?* Успешный пилот — лучший аргумент для скептиков. После его завершения мы можем масштабировать подход на самые важные домены ("Клиники"). Запуск портала самообслуживания на этом этапе — ключевой момент: бизнес-пользователи начинают получать реальную пользу (более быстрые отчеты), что создает положительную обратную связь и поддерживает мотивацию на дальнейшие изменения.

3.  **Этап 3: Закрепление успеха через управление.**
    *   *Зачем?* Data Mesh — это не только технология, но и организационная структура. После технической миграции необходимо установить новые организационные правила: кто за что отвечает? Как мы обеспечиваем качество? Без этапа внедрения управления мы рискуем получить те же хаос и низкое качество данных, но распределенные по нескольким системам. Data Contracts и каталог данных — это механизмы, которые обеспечивают слаженную работу независимых команд.

4.  **Этап 4: Фокус на росте и эффективности.**
    *   *Зачем?* Только после решения фундаментальных проблем с доступностью, качеством и скоростью получения данных можно эффективно заниматься его углубленным использованием (ML/AI) и подготовкой к стратегическим инициативам, таким как слияния и поглощения (M&A). На этом этапе архитектура из проекта трансформации превращается в конкурентное преимущество компании.
